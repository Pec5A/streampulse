# 0003 — GDPR: data export and account deletion (ticket Y2)

## Status
Accepted

## Context
The spec requires a right of access (personal data export) and a right to erasure (account deletion) compliant with GDPR. We had to decide the scope of these two operations in a repo where only the auth feature (Y1) exists yet — playlists, streams and tracks don't have tables yet (tickets K1/S1/K2, not merged).

## Decisions

### A dedicated `PersonalDataExport` type, with no password field
`ExportData` doesn't reuse the `User` entity as-is: it has a `Password` field (the bcrypt hash). A separate output type, built field by field, guarantees the hash cannot leak into the export by mistake — even after a future field gets added to `User` by someone without this context in mind. This isn't "we clean it up afterwards", it's structurally impossible to forget.

### Scope deliberately limited to user data
`ExportData` and `DeleteMe` only touch the `users` table. This is explicitly documented in `user_usecase.go`: once K1 (streams)/S1 (playlists)/K2 (tracks) are merged, the export must be extended and the deletion must cascade to them too — either via `ON DELETE CASCADE` at the schema level, or an explicit transaction here. The concrete choice will be made together with the owner of the relevant ticket, not guessed at now.

### Hard delete, no soft-delete
`DeleteMe` runs an actual SQL `DELETE`, not a `deleted_at` flag. The GDPR right to erasure (article 17) requires that the data is no longer recoverable; a soft-delete leaves the data in the database and just postpones the question — when does it get purged, under what retention policy? There's no benefit to keeping a trace here — no business constraint (billing, litigation) that would require keeping history.

## Consequences
- Any new table that references `users.id` must plan, from the moment it's created, how it will be covered by `DeleteMe` (DB-level cascade or code) — otherwise the GDPR feature silently degrades ticket after ticket.
- No grace period or deferred confirmation before deletion: `DELETE /api/v1/users/me` is immediate and irreversible on the API side. A confirmation flow (email, cooling-off period) would still need to be added on mobile if the product ever went to real production — out of scope for this academic ticket.
- The export only covers what exists in this repo today (identity). If the jury asks "what about the user's playlists?", the honest answer is: not wired up yet, documented as explicit debt above, not forgotten by accident.
